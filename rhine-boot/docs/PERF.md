# 卡顿定位报告（只读探索，未改动任何实现）

测量对象：真实构建产物 `build/index.html`（27841 字节，含注入的接管逻辑） + 真实载荷
`media/wb-rhine-splash.js`，在无头 Edge（同 Chromium 138）里跑，1280×800。

> 环境说明：无头模式用软件光栅、没有 GPU，所以"绘制/光栅"类的绝对数值会偏高。
> 但下面两条主要结论都是**主线程 / CPU** 维度的，不受 GPU 有无影响。
> 另外测试页没有真的 React，所以"宿主争用"是用**每帧占住主线程 N 毫秒**模拟出来的。

---

## 一句话结论

卡顿不在 CSS 动画里，而在**两处主线程**：

1. **首帧挂载那 0.2 秒** —— 载荷脚本求值 113ms + 整棵开屏树首次布局 96ms（522 个对象）；
2. **宿主 React 抢主线程期间** —— 每帧预算被吃掉，帧率从 120 掉到 60，文字/百分比更新少三分之一。

装饰层（点阵场、水印、玻璃面板、轨道）**不是**元凶：载荷的自适应降级 `is-lite` 几乎必然在
796–900ms 触发，用户看到的本来就是降级版。

---

## 二、证据一：首帧那一下（最主要的卡顿）

对齐后的主线程事件（相对 tracing 起点）：

| 时刻 | 事件 | 耗时 | 说明 |
| --- | --- | --- | --- |
| 86ms | `EvaluateScript` | **113.2ms** | 载荷求值，URL 指向 `media/wb-rhine-splash.js` |
| 100ms | `Layout` | **96.2ms** | `dirtyObjects=522, totalObjects=522, partial=false` —— 整棵树首次布局 |
| 200ms | `UpdateLayoutTree` | 12.3ms | 首轮样式树更新 |

DOM 打点：`mounted` 发生在 **138ms** —— 也就是说，从脚本开始求值到开屏真正画出来，
中间有约 **0.2 秒主线程是被连续占死的**。

逐帧看更直观（页面时钟 : 帧间隔）：

```
199ms : 186.5ms   ← 第一帧就等了 186ms
265ms :  66.6ms
532ms : 250.0ms   ← 74vw 位图首次上屏（解码/缩放/带 mask 的绘制在别的线程，但帧被拖住）
640ms : 108.3ms
757ms :  83.3ms
765ms 起 : 8.3ms  ← 之后完全稳定
```

### 这 200ms 花在哪：逐层消融（3 次重复取中位）

| 场景 | 首帧最长（中位） |
| --- | --- |
| 基线 | **142ms** |
| 隐藏点阵场 `.rl-field`（含 170KB base64 位图） | 117ms |
| 隐藏大字水印 | 108ms |
| 隐藏玻璃面板 `.rl-glass` | 109ms |
| 隐藏轨道/光点装饰 | 117ms |

**没有一个单一元凶**：拆掉任何一层只省 25–35ms，成本摊在"一次性建 500+ 元素 + 首帧布局"上。
换言之，这是**挂载成本**，不是某个特效的锅。

## 三、证据二：稳定播放段根本不卡

5.2 秒 trace 里，**除首帧外没有任何 >15ms 的主线程事件**。

| 指标（1.0–4.0s） | 值 |
| --- | --- |
| 帧间隔 p50 / p95 / 最长 | 8.3ms / 8.5ms / 33.4ms |
| 卡顿帧（>20ms） | 3（全在前 0.8s 的余波里） |
| 5.2s 内 `Layout` 累计 | 251ms（90% 是首帧那一次 96ms） |
| `Paint` 累计 / 次数 | 235ms / 3577 次（单次 ≤3.3ms） |
| `Layerize` 累计 / 次数 | 200ms / 531 次 |
| JS（`FunctionCall` 累计） | **55ms**，最贵的函数 `destroy` 1.1ms、`tick` 0.5ms |

52 个 `@keyframes` 里，**opacity 46 处、transform 43 处** —— 绝大部分走合成器，
主线程不参与。这就是"动画顺"的原因。

---

## 四、证据三：主线程被抢时才掉帧（真机冷启动的真实处境）

每帧人为占住主线程（模拟 React 首帧渲染）：

| 场景 | p50 | p95 | 文字更新次数 | 文字最大空档 |
| --- | --- | --- | --- | --- |
| A 无争用 | 8.3ms | 8.5ms | 413 | — |
| B 每帧占 6ms | 8.3ms | **16.7ms** | 456 | 20ms |
| C 每帧占 12ms | **16.7ms** | 16.8ms | **273（−34%）** | 27ms |
| D 每帧占 12ms + 强制 is-lite | 16.7ms | 17.6ms | 267 | 28ms |

两个关键点：

1. **C 与 D 几乎一样** → `is-lite` 降级**只省绘制，不省主线程**；
   当瓶颈是"主线程被宿主占着"时，降级毫无收益。
2. 掉帧的**表现**是"主线程驱动的那部分冻住再跳"：
   - 百分比数字 `pct.textContent`（每帧写）
   - 字符乱码 `stepScramble`（每帧写）
   - 进度条的 CSS 变量 `--rl-p` / `--rl-q`（每帧 `setProperty` → 触发 recalc）
   而 transform/opacity 的部分（门扇、光点）由合成器继续推，看起来"还在动但一卡一卡"。

## 五、证据四：`is-lite` 的采样窗口正撞在挂载停顿上

载荷逻辑：**前 400ms 量一遍帧间隔，p95 > 34ms 就降级**。
而首帧本身就是 186ms / 250ms → 几乎必然超标。

实测触发时刻：**796ms**（另一次 900ms）。
降级内容（`#rhine-splash.is-lite`）：

| 关掉什么 | 规则 |
| --- | --- |
| 点阵场位移 + 渐变蒙版 | `.rl-field { animation:none; mask-image:none; opacity:.55 }` |
| 大字水印描边 | `.rl-watermark { -webkit-text-stroke:0; opacity:.14 }` |
| 危险条纹动画 | `.rl-hazard { animation:none }` |
| 轨道 2 | `.rl-orbit--2 { animation-play-state:paused }` |
| 文字块动画 → 只留淡出 | `.rl-ch { animation-name:rl-fade }` |

**含义**：真机上你看到的已经是"轻量版"，所以再去优化这些装饰层不会有改善。

## 六、附带发现：退场段（4.0–4.5s）帧率减半

| 窗口 | 帧间隔 p50 | 说明 |
| --- | --- | --- |
| 3.0–3.5s | 8.3ms | 正常 |
| 3.5–4.0s | 8.4ms（max 49.9ms，2 个卡顿帧） | 退场前奏 |
| 4.0–4.5s | **16.6ms** | 帧率从 120 掉到 60 |

trace 里这一段**没有 >15ms 的主线程事件** → 是合成器侧：门扇 + iris 光圈 + main 淡出
+ `destroy` 同时上，属于"帧率减半"，不是"卡住"。

## 七、定位结论（按影响排序）

| # | 环节 | 量级 | 性质 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | **载荷首帧挂载** | 200–260ms | 主线程连续阻塞 | 113ms 求值（含 innerHTML 构建/解析）+ 96ms 首帧布局（522 对象） |
| 2 | **与宿主 React 抢主线程** | 每帧被吃掉 6–12ms | 帧率 120→60 | 影响的是数字/字符/进度条这类主线程驱动的部分 |
| 3 | **退场齐发** | 8.3→16.6ms | 合成器 | 门扇 + iris + 淡出 + destroy |
| — | CSS 动画本身 | 无 | 合成器 | 52 个 keyframes 里 89 处是 transform/opacity，稳态 0 个 >15ms 事件 |
| — | 装饰层（点阵场/水印/玻璃/轨道） | 各 25–35ms | 挂载期 | 且被 is-lite 常态关闭，不是主要矛盾 |

## 八、如果要动，优先级应该是什么（本次不实施）

1. 把载荷求值挪出关键路径：不要在 `</body>` 阶段同步 `innerHTML` 建 500+ 节点，
   改为先出"门扇闭合"的静态骨架（几十个节点），Act A 开始前再补齐 —— 削掉那 96ms 布局。
2. 给容器加 `content-visibility: auto` / 分段插入，避免一次性 522 个对象进同一次布局。
3. `tick()` 里三件事（百分比文字、字符乱码、两个 CSS 变量）合并成**一个**写入点，
   或降到 30Hz；它们是最先被主线程争用打死的地方。
4. 首帧的 base64 位图（170KB）延后到 Act B 再上屏，或降到 1× DPR 的小图放大。
5. `is-lite` 的判定不要用"前 400ms 帧间隔"，那一段必然超标 —— 会把轻量版变成
   "永远轻量"，反而掩盖真实性能反馈。

# 九、真实 GPU 下的复核（有头浏览器，非软件光栅）

前面几节是无头软件光栅的结果，会夸大绘制、掩盖 GPU 侧行为。用有头 Edge（真 ANGLE/GPU，
窗口挪到屏幕外 + 关闭遮挡检测）重测后，结论**需要修正一处**：

## 9.1 主线程事件（有头 trace，前 1200ms）

| 时刻 | 事件 | 耗时 | 参数 |
| --- | --- | --- | --- |
| 126ms | `EvaluateScript` | **130.6ms** | 载荷求值 |
| 143ms | `Layout` | **110.1ms** | `dirty=522/522` |
| 258ms | `UpdateLayoutTree` | 12.3ms | |
| 321ms | `Receive mojo message` | **171.0ms** | ← 渲染进程等 GPU 进程 |
| 380ms | `Receive mojo message` | 149.8ms | ← 同上 |
| 446–833ms | `ANGLEPlatformImpl::RunWorkerTask` | 17–35ms ×5 | 驱动侧首次编译/上传 |

**修正**：之前（无头）把 75ms 归给 `is-lite` 翻转，那是被"同一进程第一次跑更慢"污染的结论。
有头数据里，最坏帧出现在 **~320–400ms**，是**渲染进程阻塞在 GPU 进程消息上**
（首帧纹理上传 + 着色器编译），不是翻转本身。

## 9.2 消融（有头，单次，看同一时刻的帧）

| 场景 | ~350ms 那一帧 | ~600–700ms 那一帧 |
| --- | --- | --- |
| 全装饰（旧行为） | 217–267ms | 358ms（另有 695ms:358） |
| 去掉点阵位图 | 267ms | 158ms |
| 去掉水印+玻璃 | 242ms | 233ms |
| 首帧即降级（新行为） | 217–250ms | 108–125ms |

两个结论：
1. **~350ms 那一下（200–270ms）去不掉** —— 去掉位图、水印、玻璃都还在，是 GPU 首合成/驱动预热，
   属"进程第一次画复杂页面"的固定成本。
2. **~700ms 那一下可以削** —— 全装饰 358ms → 首帧降级后 108–125ms，因为点阵场/水印/玻璃
   在那一段本来就要重栅格一次。

## 9.3 已落地的调整（`src/stage-splash.js`，只改接管逻辑，不碰载荷）

**首帧预判降级**：载荷自己要在 `start()` 后 400ms 采样帧间隔才决定降级，
而那个窗口正好和挂载停顿重叠 → 它必然在动画播了 ~700ms 时才翻转一次。
现在改为：只要"挂载耗时"已超过它自己的阈值（34ms，实测必超），
就在 `#rhine-splash` 插入的同一拍把 `is-lite` 打上 —— 首帧即降级，不再有中途翻转。

- 终态与载荷自己判定的结果一致（都是 lite）
- 削掉 ~700ms 那一下的 240ms 左右（358 → 108~125ms）
- 刷新率/时间轴/文案全部不变；挂载快于 34ms 的机器仍走载荷原判定（保留全装饰）

## 9.4 仍未解决（需要改载荷才能动）

| 剩余卡顿 | 量级 | 位置 | 为什么改不动 |
| --- | --- | --- | --- |
| 载荷求值 | 130ms | `EvaluateScript` | 134KB 脚本 + 95KB CSS 字符串 + 170KB base64，只能拆文件 |
| 首帧布局 | 110ms | `Layout` dirty=522 | 一次建 522 个对象；`contain`/`content-visibility` 实测无效（它要的是"别一次建"） |
| GPU 首合成 | 200–270ms | `Receive mojo` / ANGLE | 驱动预热 + 纹理上传，进程级固定成本 |
